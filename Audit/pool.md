# Pool Program Security Audit

## Critical – Merkle roots are not bound to the zk-circuit outputs
* **Location.** `execute_private_transfer` and `process_unshield` both ignore the `new_root` that the Groth16 proof claims and instead compute a fresh Merkle root after appending the caller-supplied leaves.【F:programs/pool/src/lib.rs†L1098-L1115】【F:programs/pool/src/lib.rs†L1395-L1413】
* **Why it matters.** The proving circuit currently only proves that the consumed nullifiers are valid. Because it does **not** recompute the root with the output leaves, an attacker can craft a valid proof for any nullifiers and then append arbitrary output commitments on-chain. The contract blindly accepts whatever leaves are supplied, so an attacker can mint notes that were never part of the proof, fork the commitment tree, and break the conservation of value.
* **Impact.** Critical loss of funds: forged commitments can be appended without being tied to the zero-knowledge witness, letting an attacker double-spend or mint value.
* **Mitigation.** Update the transfer and unshield circuits so that the public inputs include the Poseidon root **after** adding all outputs, and make the on-chain code reject proofs whose `new_root` does not match the tree root. Until the circuit is fixed, disable private transfers/unshields or hard-stop shielded operations.

## High – Output amount commitments are never verified against the proof
* **Location.** `validate_transfer_public_inputs` explicitly states that `output_amount_commitments` never appear in the proof’s public inputs and therefore cannot be validated on-chain.【F:programs/pool/src/lib.rs†L3337-L3372】
* **Why it matters.** The ciphertext that encodes each note’s value is entirely provided by the caller. A malicious prover can generate a valid proof for spending their notes, but then append fake Pedersen commitments that encode much larger amounts. Because the pool never checks that those amount commitments came from the circuit, the note ledger accepts the forged values and inflates the pool’s accounting.
* **Impact.** High risk of silent inflation and accounting drift that auditors cannot detect, ultimately allowing drains when forged notes are unshielded.
* **Mitigation.** Extend the Groth16 circuit so that every `output_amount_commitment` is exposed as a public input (or is deterministically reconstructed from the public data), and reject transactions whose commitments do not match. Until the circuit is upgraded, block any feature that relies on those commitments (allowances, hook logic, invariant checking) and treat every transfer as untrusted.

## High – Allowance spending trusts attacker-supplied amounts
* **Location.** `transfer_from` only checks that `allowance_amount == spend_amount` (two user-supplied integers) before decrementing the allowance; it never re-computes how much value is actually transferred in `TransferArgs` because those amounts are not present in the proof.【F:programs/pool/src/lib.rs†L952-L980】【F:programs/pool/src/lib.rs†L2267-L2281】
* **Why it matters.** A malicious spender can build a proof that moves the owner’s entire balance to themselves but set `spend_amount = 1` and `allowance_amount = 1`. The pool dutifully reduces the allowance by one unit even though the proof may transfer an arbitrarily large amount, letting the attacker drain the allowance owner’s notes while barely touching the allowance state.
* **Impact.** High risk of unauthorized balance transfers via the allowance API, completely defeating delegated spending limits.
* **Mitigation.** Either (a) remove `transfer_from` until the circuit exposes the true spend value as a public input, or (b) recompute the spend amount on-chain (e.g., have the circuit emit it in the public inputs and cross-check it before mutating the allowance account).
